# 26Anlu-vision

B 板视觉控制系统 —— 安路 **EG4S20BG256**（康芯 HX4S20C 板）+ **OV5640** 摄像头，
按 `docs/implementation-plan.md` 分 8 个 Phase 推进：采集 → 片内 SDRAM 帧缓冲 → YCbCr →
HDMI 显示，再逐级叠加火灾 / 烟雾 / 运动 / 手势识别与通信中转。

| 4–8 | 烟雾 / 运动 / 手势 / 通信 / 集成 | 未开始 |

## 数据通路

```
ov5640_dri (SCCB 配置 + DVP 采集, RGB565)
  → ov5640_delay (RGB565→RGB888, 打包 {R,G,B,8'd0})
  → frame_read_write (写: cam_pclk 域 / 读: video_clk 域, 内部异步 FIFO 仲裁)
      ↑ 基址由 frame_buffer_ctrl 按帧提交在 BUF0/BUF1 间交替 (0 / 307200 字)
  → sdram (片内 2M×32, EG_PHY_SDRAM_2M_32 硬宏, 引脚不得写进 .adc)
  → display_path (rgb_to_ycbcr 两级流水 + 模式 mux + video_delay PIPE_LAT=2 对齐)
      ├─ 检测支路 (Phase 3, 分用同一条读通道): fire_detector (色域, 纯组合)
      │    → fire_region_analyzer (8×8 块密度 → 帧面积 → 漏桶确认 → 质心 → 蒙版乒乓 RAM)
      │    → 50% 半透明红叠加 + 右上角 4 格 HUD, 全部是组合选择, 不加寄存级
      └→ hdmi_tx (VHDL, TMDS LVDS)
```

关键数字：显示 640×480@59.5Hz（25MHz / 800×525），采集 1856×984@24MHz ≈ **13.1fps**，
一帧 307200 字 = `BURST_SIZE(256)` 的整数倍（这条必须成立，否则最后一轮突发会越界写进
另一块缓冲），两块共占片内 SDRAM 的 29%。**读比写快 4.6 倍**是双缓冲不撕裂的依据：
写指针绕回读侧正在显示的那一块时，读头始终领先。

## 板级判据（上电后一眼能读的东西）

| 丝印 | 球号 | 含义 |
|---|---|---|
| led1 | A4 | 常亮 = OV5640 SCCB 配置表写完 |
| led2 | A3 | 常亮 = 片内 SDRAM 初始化完成 |
| led3 | C10 | **闪 0.93Hz = 读通道活着**（每读完一帧翻转一次，59.5Hz/32） |
| led4 | B12 | **闪 0.82Hz = 写通道在提交整帧**（13.1Hz/8） |
| dled | A8 / A7 | 摄像头出帧 / 显示时序心跳，各约 0.8Hz |

指示器一律用**事件翻转计数**，不用"展宽脉冲"：亮灭各半才可判读，展宽脉冲的占空比一旦
接近 50% 肉眼看就是常亮（这一条本项目踩过坑）。

### Phase 3 新增：右上角 4 格 HUD（画面内，2 块高 = 16 行，每格 8 像素宽，黑底 = 灭）

检测器的状态没有串口可看，所以把它画在画面右上角——**四档模式下都画**（含彩条档），
切到调试档时检测器状态仍然可读。

| 格（从左到右） | 颜色 | 亮 = | 灭而别处正常 = |
|---|---|---|---|
| 1 | 蓝 | 检测遍心跳（0.93Hz 明暗各半）→ 分析器在收遍 | `de_cap`/`pass_end` 没来，检测器根本没跑 |
| 2 | 黄 | 本遍有候选像素（色域判据命中过） | 门限太高，或场景确实没暖色 |
| 3 | 橙 | 本遍有块过了密度门限（蒙版里确有红块） | 只有散点，没成块 |
| 4 | 红闪 | 报警中（1.98Hz） | 未达 6 块，或未到连续 3 遍 |

判读顺序：先看蓝格在不在闪（检测器活着）→ 再对着场景看黄/橙 → 最后看红。
**注意检测的时间单位是"显示遍"（59.5Hz）不是相机帧（13.1fps）**：同一相机帧被重复判约
4.55 遍，所以 `SET_N=3 遍 ≈ 50ms`；把遍数换算成帧要除以 4.55。

上板看 HUD 之前的前提条件（少一条就没法判读）：

1. `led1`、`led2` 常亮（SCCB 配完 + SDRAM 初始化完），且 HDMI 有画面——没画面时先回彩条档
   （`key2` 切到 3 档）确认显示链路，再回 0 档。
2. 档位必须在 0/1/2 三档之一：彩条档（3）刻意不叠蒙版，只画 HUD，所以那时**画面里没有红块
   是正常的**，HUD 四格仍然有效。
3. 目标要够大：报警门限是 6 个块 ≈ 48×48 像素 ≈ 全帧 0.125%，蜡烛火焰要占满这么大的区域
   （约 195×195 像素的框，等于让火苗占到画面宽度的 1/3）。距离太远时只会点黄格不点橙格。
4. 蒙版比画面晚一遍（≤16.8ms，乒乓 RAM 的代价），快速移动火焰时红块会拖在后面，**不是 bug**。
5. 肤色、木色、灯光反光要能只点黄格不点橙格（块密度门限的作用）；对着一面白墙应该四格全灭
   （蓝格仍然闪）。

`key2`(B2) 切显示档位，`key1`(A2) 复位：

| 档位 | 显示 | 数据来源 |
|---|---|---|
| 0 | 原图 RGB | 帧缓冲 |
| 1 | 灰度（77R+150G+29B） | 帧缓冲 |
| 2 | 伪彩 R=Y, G=Cb, B=Cr | 帧缓冲 |
| 3 | **8 列彩条** | 内部计数器，完全绕开帧缓冲 |

第 3 档是调试档：它把"HDMI/显示器/同步这条链路是否活着"与"帧缓冲内容对不对"分开判断。
彩条按 `read_en` 计数（与显示像素同序），按 `de_i` 计会超前流水线深度而在行首行尾露白。

## 回归

```bash
sh sim/run_all.sh          # 需要 D:/iverilog/iverilog/bin 在 PATH 里
```

- 第 0 步按 `26Anlu-vision.al` 自己的文件清单跑 iverilog 并扫 "Unknown module"，等价于 TD 的
  black box 检查（加密 IP 与 TD 生成的 `ip/*.v` 用 `sim/lint_stubs.v` 顶替）。
  **注意它把输出管道给了 grep，所以语法/位宽错误不会显示**——"登记完整 ✓" 只代表没扫到黑盒；
  改完 `top.v` 要把那条 `iverilog -g2012 -tnull -s top $ALFILES sim/lint_stubs.v` 单独跑一遍
  看全量输出
- `tb_rgb_to_ycbcr`：4264 像素逐位比对，值域实测 Y[16,235] Cb/Cr[16,240] gray[0,255]
- `tb_frame_buffer_ctrl`：按真实读写速率比建模，代标记分板 + 无撕裂判据
- `tb_display_path`：**真实** `frame_read_write` + 真实异步 FIFO 的端到端像素对齐，
  四档全过，并断言 `App_wr_en` 与 `App_rd_en` 永不同拍（仲裁互斥被破坏时，像素位置/颜色
  检查全都发现不了，只有这条能报）
- `tb_fire_detector`：色域判据真值表（含"暗橙过不了 Y 坎、肤色过不了 Cr-Cb 坎"两条反证）、
  块密度门限、报警置位/撤销漏桶、质心除法器、蒙版逐地址回读
- `tb_fire_overlay`：真实读通道下的**蒙版落位**端到端 —— 96×48 = 12×6 块的四类区域
  （亮橙火焰 / 暗橙 / 肤色带 / 灰墙）逐像素判读：该标红的标了且位置逐像素正确、不该标红的
  原样显示、右上角 HUD 只在它那 4 列出现、彩条档蒙版整体消失。
  ★ 这个 TB 踩到的两个节拍坑都写在其源码注释里，改 TB 节拍前必读：**帧周期必须大于一个
  显示遍周期**（双缓冲不防"写头追上读头"），以及**彩条档的条号是全局 `read_en` 计数**
  （条计数器不按行/不按遍复位）

`src/sdram/enc_file/*.enc.v`、`src/hdmi/enc_file/*.enc.vhd` 是加密 IP，iverilog 读不了，
所以只有纯 RTL 部分能本地仿真。

## 时序

`phy_1/final_timing.rpt` 逐时钟汇总（Phase 3 编译后，按周期识别时钟域，TD 的 clk0/clk1 编号
在不同编译里会变）：

| 时钟域 | 约束周期 | 实测最小周期 | SWNS | 该域 Fmax |
|---|---|---|---|---|
| `mem_clk` 125MHz | 8.000ns | 6.340ns | **+1.660ns** | 157.7MHz |
| `video_clk` 25MHz（检测逻辑在此域） | 40.000ns | 21.055ns | **+18.945ns** | 47.5MHz |
| `cam_pclk` | 40.000ns | 6.413ns | +33.587ns | 155.9MHz |

STNS/HTNS = 0，**0 个违例端点**，hold 最差 +0.118ns。资源：LUT 2969/19600 = 15.2%
（Phase 2 是 1544 = 7.9%），ERAM9K 8/64 = 12.5%（Phase 2 是 6 块，**新增的 2 块正是
`mask0`/`mask1`** —— 综合日志 `SYN-1026 : Infer Logic BRAM(u_disp/u_fire_region/ramread0_syn_4)`
与 `ramread1_syn_4` 确认 1-bit 蒙版数组真的推断成了 ERAM，没有退化成 LUTRAM/触发器）。

蒙版 RAM 的上电内容是随机的（TD 提示 `eram_init is set to off`，即 init 值被忽略），
这不构成问题：`mask_valid` 要等一整遍写完才允许叠加，而叠加时读的必然是刚写完的那块银行
（乒乓），所以随机内容永远不会被显示出来。

`mem_clk` 域曾经是 `frame_fifo_write` 里 `write_len_latch <= (rdusedw + write_cnt)` 一个表达式
造成的唯一 setup 违例：FIFO 指针相减的 5 级 ADDER 后面又串了 2 级加法 + 21 位幅值比较，直达
读侧 FSM。改法见 `src/memory/frame_fifo_write.v` 注释。报告位置：`26Anlu-vision_Runs/syn_1/run.log`
（登记与 black box）、`phy_1/final_timing.rpt`（逐端点单元/网络延迟表）。

## 已知残留

**写突发的可用字数余量只有 0~1 个字**：`frame_fifo_write` 的 `into_burst` 有两个条件。
`burst_need <= rdusedw` 那一支只在**一帧的最后一轮突发**才可能成立（`burst_need` 是
`write_len_latch - write_cnt` 饱和到 512 的结果，帧中间每轮剩余字数都 > 512，而 512 深
FIFO 的 9 位 `rdusedw` 最大 511）；其余轮次靠 `rdusedw > BURST_SIZE`，也就是"攒够 257 个
字才发一轮 256 字的突发"。用一次性探针（打印每轮突发起点的 `rdusedw`/`burst_need`/
`write_cnt`，查完已删）实测过：`rdusedw` 稳定落在 256~257（帧尾那轮是 256，余量 0），
写进显存的字全都有定义、逐窗口显存对账 0 错。但 `rdusedw` 是跨时钟域同步后的计数，余量这么小意味着上板后要专门盯：Phase 8
拷机若出现规律性的横条错位，第一嫌疑就是这里读空了。抬门限（比如要求 `rdusedw ≥ 264`）是
一个一行改动的选项，代价是每轮多等 8 个字，需要时再做。

读侧基址在 `S_ACK` 那拍锁存，而 `rd_index` 要先过 2 级同步，所以提交若落在该 16ns 窗口内，
那次读会锁到旧索引 → 读到正在被写的那块，出现**一帧**撕裂，下一帧自愈。按 59.5 帧/s × 16ns ×
13.1 次提交/s 估算约 **22 小时一次**。单独为它上第 3 块缓冲不划算；Phase 5 的帧间差分本来要
复制 `frame_fifo_read` + 读 FIFO（Phase 3 的火焰检测分用了显示读通道，没走到这一步，理由写在
`docs/implementation-plan.md` 的 Phase 3 一节），那时顺手把 3 缓冲一起上（`read_addr_2` 槽位现成）。
